# AGENTS.md

`autotest-e2e` проверяет `qa-course-app` через браузер и HTTP. Стек проекта — Python, Poetry, pytest, Playwright, HTTPX и Loguru. Команды локального запуска и адреса стенда описаны в [README](README.md).

Сверяй ожидания с требованиями и контрактом проверяемой ревизии стенда. Для HTTP используй её OpenAPI и документацию приложения. Код и тесты из `autotest-api` и `ui-tests` служат примерами реализации. При расхождении документации и поведения зафиксируй его явно.

## Работа в Git

- Основная ветка — `main`. Создавай ветку или PR по отдельному запросу пользователя.
- Сохраняй чужие изменения. Для разрешённого коммита выбирай только файлы или строки задачи и используй Conventional Commits. Отправляй изменения на GitHub в рамках разрешения пользователя.

## Структура тестов

- Размещай сквозные сценарии в `tests/e2e/`, а точечные проверки по мере появления — в `tests/api/` и `tests/ui/`. Предметные сценарии группируй в классы `Test<Domain>`. Передавай фикстуры аргументами методов. Состояние отдельного сценария держи в фикстурах и локальных переменных. Называй тесты по проверяемому поведению.
- Тест описывает исходные данные, ключевое действие и ожидаемый результат. Фикстуры подготавливают предпосылки и отвечают за очистку. Оставляй в тесте существенные действия и вызовы проверок. Доменные проверки, их Allure-шаги и Loguru-сообщения держи в `tools/assertions`.
- В `clients/` держи HTTPX-транспорт, доменные методы и модели запросов и ответов. Транспорт возвращает `httpx.Response`, чтобы тест мог проверить любой статус и тело. Общие обёртки для успешной подготовки данных могут возвращать разобранную модель.
- В UI следуй цепочке **Tests → Pages → Components → Elements → Playwright**. Page Objects в `pages/` отвечают за маршруты и состояние страницы. `components/` работают внутри конкретной формы, карточки или диалога. `elements/` содержат повторяемые действия и атомарные проверки. В `fixtures/` связывай клиентов, страницы и жизненный цикл данных. Добавляй эти слои по мере необходимости первого и следующих сценариев.

## Докстринги

- Добавляй докстринг к каждой новой функции и каждому новому методу, включая тесты, фикстуры и внутренние функции. Для очевидного контракта достаточно одной строки о назначении или результате.
- Для нетривиального контракта используй Google-style. После краткого резюме оставь пустую строку и добавь нужные разделы `Args`, `Returns`, `Yields` и `Raises`. Указывай существенные ограничения, побочные эффекты и очистку. Для теста описывай проверяемый сценарий и важные предпосылки.
- Пиши докстринги по-русски, сохраняя технические термины и названия разделов Google-style. У каждой схемы API опиши назначение. Типы оставляй в аннотациях.

## HTTP и UI

- В `APIRoutes` храни корневые маршруты ресурсов, а суффиксы операций собирай в клиентах. URL и таймаут бери из `config.settings`. Фикстуры размещай в `fixtures/` и подключай в `conftest.py` через `pytest_plugins`.
- Для API проверяй статус до разбора успешной схемы. Проверяй конкретную сущность и нужные поля, а для сохранения сделай отдельное чтение. Для негативного случая убедись, что запрос с нужным невалидным значением дошёл до сервера.
- В моделях сохраняй имена полей HTTP-контракта. Для PATCH с Pydantic используй `exclude_unset=True`, чтобы различать пропущенное поле и явно переданный `null`. Сохраняй явно переданные `0`, `false` и пустые строки, когда их допускает контракт.
- В UI используй устойчивые `data-testid`, роли и подписи. Для повторяющихся элементов сначала выбери нужную карточку по UUID, например через `data-course-id` или `data-exercise-id`. Позиционный селектор подходит, когда сценарий проверяет порядок.
- Жди наблюдаемого результата через Playwright `expect`. Ожидания браузерных событий размещай в Page Objects. Если запрос входит в предмет проверки, поставь ожидание до действия и сопоставь метод, маршрут и сущность. Для проверки сохранения повторно открой нужную запись или обнови страницу и сверь поля.
- В сквозных проверках сохранения используй реальный API стенда. Подмена ответа подходит для отдельной проверки реакции интерфейса на ошибку. Проверка обложки требует реальной загрузки файла.

## Изоляция и диагностика

- Для изменяющих сценариев используй уникальные тестовые аккаунты и данные. Новый контекст браузера изолирует сессию браузера. Серверные данные изолируй отдельно, в том числе между pytest-воркерами.
- Регистрируй очистку после каждого успешного создания ресурса, чтобы она срабатывала и при частично упавшей подготовке. Удаляй только созданные тестом записи по UUID. Для курсов сначала удали курс с зависимостями и отдельно загруженные непривязанные файлы, затем аккаунт. Закрытие клиента и удаление данных входят в teardown.
- Показывай обычные тестовые параметры и модели в Allure и диагностических Loguru-логах. Используй `log_model` для записи моделей.
- Для HTTP-логов достаточно метода, безопасного пути и статуса. Убирай пароли, токены, cookies и `Authorization` из логов, cURL и отчётов до их записи. Проверяй браузерные trace, скриншоты и видео перед опубликованием. Учётные данные и локальные артефакты держи вне Git.

## Проверка изменений

- Проверяй актуальность lock-файла командой `poetry check --lock --strict`. Для Python-изменений запускай `poetry run ruff format --check .`, `poetry run ruff check .` и `poetry run mypy .`.
- Запускай затронутые pytest-сценарии против выделенного тестового стенда и фиксируй, что подтверждено прогоном. При нестабильности разбери первую неудачу по логам или trace. Привязывай ожидания к наблюдаемому состоянию вместо фиксированных пауз.
- В CI закрепляй ревизию `qa-course-app`, жди готовности сервисов Compose и очищай только контейнеры и тома своего прогона. Доступ на чтение приватного репозитория приложения передавай через секреты CI.
